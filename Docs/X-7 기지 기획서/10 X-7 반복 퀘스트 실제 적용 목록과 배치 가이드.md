**현재 반복 퀘스트는 모두 샘플 납품형이다.** 에셋은 11개이고, 실제 계약 추첨 풀에 등록된 것은 8개다. 화면에 벽 철거·청소·스캔·폐기물 수거라고 나오는 항목도 실제 `ObjectiveType`은 회수형으로 설정되어 있다. 아래의 **실제 완료 조건**을 배치 기준으로 사용한다.

기존 기획 문서의 목표·장소·보상은 근거로 사용하지 않았다. 데이터 에셋 속성과 현재 C++ 실행 경로를 대조했다. 이번 작업은 읽기 전용 조사와 문서 작성이며, 게임 설정을 수정하거나 PIE 완료 테스트를 새로 수행하지 않았다. 조사 시 에디터의 미저장 맵·에셋은 없었다.

## 2. 모든 반복 퀘스트에 공통으로 적용된 설정

11개 에셋의 모든 페이즈가 다음 설정을 공유한다.

| 속성 | 현재 값 / 동작 |
|---|---|
| `SpawnZoneTag` | `Env.Zone.Mothership` |
| `RequiredItemClass` | `None` — 선택된 스포너의 `SampleClass` 사용 |
| `RequiredItemDefinition` | `None` — 현재 핫바 카트리지 납품형으로 설정되어 있지 않음 |
| `PhaseCompletionReward` | 크레딧·점수·호감도 모두 0 |
| 현재 일반 스포너의 `SampleClass` | `/Game/Blueprint/Sample/BP_SampleBase.BP_SampleBase_C` |
| 샘플 귀속 | 생성 시 `QuestDefinitionId=Quest:X7_Rxx` 자동 지정 |

**구역 태그는 정확히 일치해야 한다.** `Env.Zone.Station`, `Env.Zone.X7` 또는 자식 태그를 넣는다고 `Env.Zone.Mothership` 퀘스트가 연결되지는 않는다. 태그는 실제 좌표·방 이름을 자동 판별하지 않는다.

현재 구성에서는 저장고·심층 협곡·생물실험동 같은 HUD 장소 표현이 스폰 위치를 제한하지 않는다. 모두 같은 `Mothership` 후보군을 사용한다. 스포너 라벨에 `R02`, `R10`을 붙여도 퀘스트 전용으로 연결되지 않는다.

### 생성 수량과 Arrow의 실제 의미

1. 플레이어가 반복 퀘스트를 수락하여 `Accepted` 상태가 되어야 스폰을 시도한다.
2. 매니저가 **퀘스트 ID + 페이즈 인덱스마다 후보 스포너 한 개**를 무작위 선택한다.
3. 선택된 스포너가 `요구 수량 - 납품 진행도 - 해당 퀘스트의 기존 유효 샘플 수`만큼 생성한다.
4. 생성 위치는 그 스포너에 붙은 `ArrowComponent` 배열을 순환한다. 코드가 `Index % Arrow 개수`를 사용하므로 Arrow가 부족하면 같은 위치가 다시 사용된다.

**반복 퀘스트 경로에서 `SamplesToSpawn` 값은 생성 수량을 결정하지 않는다.** 현재 인스턴스 값이 1이어도 R07은 부족분 5개를 생성한다. 5개를 분산시키려면 후보 스포너 **각각**에 서로 떨어진 Arrow 5개가 필요하다. 1개짜리 스포너를 5개 배치하는 것만으로 5개 위치에 분산되지 않는다.

등급은 `AcceptedGradeTags` 중 첫 번째 지원 등급으로 생성한다. R02의 현재 태그 순서는 C, B이므로 자동 생성은 **C급 2개**다. 납품 조건은 B도 허용하지만, 자동으로 C와 B를 섞어 생성하지 않는다.

에디터에 현재 로드된 `L_Ocean`에서 확인한 일반 스포너다. 좌표 단위는 cm, 소수점은 반올림했다. 미로드 레벨 전체를 별도로 열어 조사한 결과는 아니다.

| 아웃라이너 라벨 | 실제 `SpawnZoneTag` | 위치 X / Y / Z | Arrow 수 | 현재 반복 퀘스트 후보 |
|---|---|---|---:|---|
| `BP_QuestSampleSpawner` | `Env.Zone.Mothership` | -1688 / -794 / 349 | 1 | 해당 |
| `BP_QuestSampleSpawner2` | `Env.Zone.Mothership` | 126 / 253 / 260 | 1 | 해당 |

모두 `SampleClass=BP_SampleBase`, `SamplesToSpawn=1`, `SampleSpawnProtectionDuration=3.0`이다. 일반 스포너 Blueprint 자체의 Zone 기본값은 `None`이므로 **새로 배치할 때 인스턴스의 태그를 지정해야 한다.**

**현재 배치에서 주의할 점:** 모선 후보 3개 모두 Arrow가 1개다. 다수 샘플은 동일 위치에 생성될 수 있고, 생성 옵션도 `AlwaysSpawn`이므로 충돌로 자동 분산되지 않는다. 서로 다른 수락 퀘스트가 같은 후보 스포너를 고르는 것도 가능하다. 퀘스트 간 자리 예약·배타 선택은 없다. 실제 겹침·충격·낙하 여부는 PIE에서 확인해야 한다.

## 4. 공통 배치 절차 — 현재 구현을 유지하는 방법

아래는 앞으로 배치할 때의 작업 절차다. 문서 작성 과정에서 이 변경을 적용하지는 않았다.

1. `L_Ocean`을 열고 `/Game/Blueprint/Sample/BP_QuestSampleSpawner`를 사용할 위치에 배치한다.
2. Details의 `MD | Quest | Spawn`에서 `SpawnZoneTag`를 **`Env.Zone.Mothership`**으로 지정한다. 새 Blueprint의 기본 태그가 비어 있는 점을 확인한다.
3. `SampleClass`가 **`BP_SampleBase`**인지 확인한다. 현재 모든 반복 퀘스트의 `RequiredItemClass`가 비어 있어 이 설정이 실제 생성 클래스를 결정한다.
4. 스폰 후보마다 Arrow를 최소 5개 준비한다. 여러 인스턴스에 공통 적용하려면 별도 자식 Blueprint에 Arrow를 구성하는 방법을 권장한다. 이는 최대 요구량인 R07까지 위치를 분산하기 위한 배치 권장사항이며 현재 적용 상태는 아니다.
5. 각 Arrow를 바닥·선반 위의 서로 겹치지 않는 위치에 둔다. 간격은 실제 샘플 충돌 크기보다 넓게 잡고, 콜리전 내부나 낙하 구멍 위를 피한다. Arrow의 월드 스케일이 샘플에 반영되므로 불필요한 스케일 변경을 피한다.
6. 후보 3곳 중 어느 곳이 선택되어도 생성·접근·회수가 가능해야 한다. 한 후보에만 충분한 Arrow를 만들어 두면 다른 후보가 선택될 때 겹침이 남는다.
7. 스폰 지점은 납품 선반의 `CollectionVolume` 밖에 둔다. 선반은 볼륨 안의 손에서 떨어진 퀘스트 아이템을 수거하며, 미리 겹쳐 있는 아이템도 검사한다.
8. `BP_SampleShelf`까지 손으로 운반 가능한 통로와, 이후 상인에게 가서 보상을 받는 동선을 확보한다.

현재 데이터 그대로는 ‘R02는 저장고에서만’, ‘R11은 B1에서만’ 같은 **퀘스트별 장소 고정이 불가능**하다. 후보 한 곳을 특정 방으로 옮기더라도 모든 같은 Zone 퀘스트가 그곳을 선택할 수 있다. 장소별로 분리하려면 해당 페이즈의 `SpawnZoneTag`와 해당 스포너의 태그를 함께 바꾸는 데이터 수정이 필요하며, 이는 이 문서에서 설명하는 현재 설정과는 다른 작업이다.

## 5. 퀘스트별 배치 가이드

아래 각 항목은 공통 절차를 사용한다. 현재 8개는 **동일한 모선 후보 3곳을 공유**한다. 표의 Arrow 수는 해당 퀘스트만 볼 때 필요한 분산 위치 수이며, 풀 전체를 지원할 후보에는 최대값 5개를 준비한다.

### R02 · 저장고 샘플 추가 수집

- 에셋: `/Game/Data/Quest/X7/Repeat/X7_R02`
- 실제 목표: `RecoverDamaged`, C/B 허용, 2개. 자동 생성은 C급이다.
- 배치: 선택되는 후보 스포너에 Arrow **2개 이상**, `SampleClass=BP_SampleBase`, Zone `Env.Zone.Mothership`.
- 회수: 온전하거나 손상된 샘플 2개를 선반에 납품한다. 완전 파괴와 손상 허용을 혼동하지 않는다.
- 확인: HUD에 ‘07 저장고’가 있어도 현재 저장고 전용 연결은 없다. C급 2개가 실제 수락한 R02 ID로 생성되고 납품 2/2가 되는지 확인한다.

### R05 · 보존실 진입로 확보

- 에셋: `/Game/Data/Quest/X7/Repeat/X7_R05`
- 실제 목표: `RecoverIntact`, C급 1개.
- 배치: Arrow **1개 이상**에서 C급 샘플을 생성한다. 일반 회수 동선이면 된다.
- 확인: 벽을 절단하거나 마감한 것만으로 이 목표를 충족했다고 판정하면 안 된다. 현재 데이터는 **샘플 1개 납품**을 요구한다.
- HUD ‘B1 인근의 막힌 입구 벽을 철거하고 마감’과 실제 목표가 불일치한다. 이 문구대로 작동시키려면 별도 기능·데이터 수정이 필요하다.

### R09 · 진입구 안전화

- 에셋: `/Game/Data/Quest/X7/Repeat/X7_R09`
- 실제 목표: Phase 0 C급 온전 1개 → Phase 1 C급 온전 1개. 둘 다 `RecoverIntact`.
- 배치: 페이즈별 Arrow **1개 이상**이면 된다. 2개를 처음부터 고정 배치하는 대신, 수락 후 첫 샘플을 납품하면 다음 페이즈 스폰이 일어나는 흐름을 사용한다.
- 확인: 첫 납품 후 페이즈가 바뀌고 진행도가 0으로 초기화되는지, 다음 샘플을 납품하면 마지막 목표가 완료되는지 확인한다. 페이즈마다 후보를 독립 선택하므로 두 번째 샘플은 다른 후보에서 나올 수 있다.
- 첫 HUD의 ‘청소하고 절단면 마감’은 실제 조건과 다르다. 청소·마감용 액터를 놓는 것만으로 첫 페이즈를 대체할 수 없다.

### R10 · 생물실험동 회수

## 6. 납품 선반과 보상 수령

현재 `L_Ocean`에서 다음 두 액터를 확인했다.

| 액터 | 위치 X / Y / Z | 역할 |
|---|---|---|
| `BP_SampleShelf` | -489 / -355 / 142 | 샘플 수거·퀘스트 진행도 반영 |
| `BP_MD_Merchant` | -919 / -168 / 136 | 반복 퀘스트 수락 및 최종 보상 수령 UI |

선반 Blueprint 경로는 `/Game/Blueprint/Sample/BP_SampleShelf`다. 현재 인스턴스 `CollectionVolume`은 `QueryOnly`, `Generate Overlap Events=true`이며 월드 스케일 적용 후 Box 반크기는 약 X 69.87 / Y 79.06 / Z 105.13cm다. 이 값은 전체 폭·높이가 아니라 **반크기**다.

플레이 흐름은 다음과 같다.

1. 상인 UI에서 제시된 반복 퀘스트를 수락한다.
2. 생성된 해당 퀘스트 샘플을 손으로 운반한다.
3. 선반의 `CollectionVolume` 안에서 손에서 놓는다. 손에 들고 있는 동안은 수거하지 않는다.
4. 선반이 샘플을 제거하고 유효 납품이면 퀘스트 진행도를 올린다. 전시 메시가 남더라도 실제 샘플 액터와는 다르다.
5. 마지막 목표를 채운 뒤 상인 UI의 보상 수령을 처리해야 `Completed`가 되고 성공 보상이 지급된다. 납품 수량을 채우는 것과 보상 수령은 별도 단계다.

**전시되었다고 퀘스트에 인정된 것은 아니다.** 납품 경로는 해당 아이템을 제거하면서 조건을 만족하는 퀘스트에만 진행도를 반영한다. 귀속 ID가 틀리거나 온전 조건을 만족하지 않으면 선반으로 들어가도 목표 수량이 오르지 않을 수 있다.

일반 샘플을 직접 배치한 경우 `QuestDefinitionId`가 자동으로 반복 퀘스트에 연결되는 것으로 가정하지 않는다. 반복 경로는 스포너가 새로 생성할 때 ID를 지정한다. 현재 구현 그대로 검증할 때는 일반 스포너의 수락 후 생성 흐름을 사용한다.

## 7. 실패 수치

표는 실제 차감량이다. 데이터 에셋에는 양수로 저장되어 있지만 실패 적용 함수가 패널티 방향으로 처리한다. 모든 항목의 크레딧 차감은 0이다.

| 에셋 | 미회수·중도 포기: 점수 / 호감도 차감 | 파괴: 점수 / 호감도 차감 |
|---|---|---|
| R01 · 풀 제외 | 0 / 0.1 | 0 / 0.4 |
| R02 | 55 / 0.1 | 0 / 0 |
| R03 · 풀 제외 | 0 / 0.1 | 0 / 0.4 |
| R04 · 풀 제외 | 0 / 0.2 | 0 / 0.4 |
| R05 | 0 / 0.1 | 0 / 0 |
| R06 | 0 / 0.1 | 0 / 0 |
| R07 | 0 / 0.1 | 0 / 0 |
| R08 | 55 / 0.2 | 0 / 0 |
| R09 | 20 / 0.1 | 45 / 0.2 |
| R10 | 70 / 0.4 | 85 / 0.4 |

파괴 패널티 0은 실패하지 않는다는 뜻이 아니다. 활성 퀘스트에 귀속된 목표 등급 샘플의 파괴 통지가 오면 실패 처리될 수 있다. 계약 종료 시 미완료인 수락 퀘스트도 미회수 실패 처리된다.

## 8. 배치 후 확인할 항목

아래는 실행할 테스트 목록이며 이번 문서 조사에서 통과한 항목으로 표시한 것이 아니다.

- 새 계약에서 8개 풀 중 2~3개가 제시되고, R01·R03·R04가 나오지 않는지 확인한다.
- 해당 퀘스트 수락 후 선택된 스포너·등급·개수가 맞는지 확인한다. 로그에서 `QuestSampleSpawnerManager`의 선택 기록과 `QuestSampleSpawner`의 반복 퀘스트 생성 기록을 본다.
- 후보 3곳 각각에서 R07 5개가 겹치거나 떨어져 파괴되지 않는지 확인한다. 여러 퀘스트를 동시에 수락하는 경우도 확인한다.
- 손에 든 채 선반 볼륨을 통과할 때는 수거되지 않고, 놓았을 때만 진행도가 오르는지 확인한다.
- R02·R08은 손상 허용, 나머지는 온전 조건인지 확인한다. 샘플 등급뿐 아니라 귀속 퀘스트 ID를 확인한다.
- R09 첫 납품 후 다음 단계 샘플이 생성되고, 두 번째 납품 후 보상 수령이 가능한지 확인한다.
- 목표 완료 후 상인 UI에서 보상을 수령하고 상태·크레딧·점수·호감도를 확인한다.
- 세이브 복원 시 이전 계약·수락 상태가 남을 수 있으므로, 신규 계약 테스트와 이어하기 테스트를 구분한다. 기존 사용자 세이브를 임의 삭제하지 않는다.

## 9. 근거와 확인 범위

실제 값은 `Saved/Diagnostics/RepeatQuestGuide_20260928/`에 조회 결과로 보관했다. `quests.json`은 11개 에셋의 기본값까지 해석한 목표·보상, `asset-values.json`은 Site 풀과 원본 속성 텍스트, `spawners.json`은 현재 배치·태그, `delivery.json`은 납품 액터 조회 결과다.

실행 규칙의 근거 파일:

- `Source/MarineDemolition/Private/Gameplay/Merchant/MD_MerchantSubsystem.cpp`: 계약 추첨, 수락, 납품 진행, 최종 수령, 실패 정산.
- `Source/MarineDemolition/Private/World/Sample/MD_QuestSampleSpawner.cpp`: 반복 수락 상태 검사, 부족분 생성, 클래스·등급 결정, 정확한 Zone 일치, Arrow 순환.
- `Source/MarineDemolition/Private/World/Sample/MD_QuestSampleSpawnerManager.cpp`: 퀘스트·페이즈별 후보 하나 선택 및 캐시.
- `Source/MarineDemolition/Private/Data/Merchant/MD_QuestDefinition.cpp`: 온전·손상 허용·등급 판정.
- `Source/MarineDemolition/Private/World/Sample/MD_SampleShelf.cpp`: 놓은 아이템 수거, 납품 호출, 전시 처리.
- `Source/MarineDemolition/Private/UI/Merchant/MD_QuestWidget.cpp`: 보상 수령 버튼 연결.
