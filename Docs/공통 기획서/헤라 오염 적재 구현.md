# 헤라 오염 적재 — 구현 기준

**갱신:** 2026-09-18. 현재 구현의 적재 +1.0·67부터 제거 중단·역오염 10%를 유지하기로 합의했다. 이 문서는 이전의 +0.6·40%와 “포화 상태에서도 청소 가능” 설명을 대체한다.

헤라로 닦으면 날에 오염물이 쌓인다. 적재가 67에 도달하면 더는 닦이지 않고, 오히려 닿은 곳에 오염이 묻는다. 쓰레기통에 털어 67 미만으로 내려야 다시 닦을 수 있다.

관련 문서: [시스템 §1.2](02%20시스템%20기획.md), [아이템 §2.0](08%20아이템%20기획.md), [구현 대조 §4·§10](15%20구현%20대조%20및%20플레이%20검증%20기획.md).

## 1. 확정한 규칙

| 항목 | 기준 |
|---|---|
| 적재 범위 | 0~100. 시작 0, 시간이나 수영으로 자연 감소하지 않음 |
| 오염 제거에 따른 적재 | 실제 오염 제거율 1%당 **+1.0** |
| 따개비 | 기존 **1개당 +8** 기획 유지 |
| 적재 67 미만 | 정상 청소 |
| 적재 67~100 | **오염을 제거하지 않음**. 해당 접촉의 요청 작업량 중 **10%**를 역오염으로 더함 |
| 포화 중 적재·신규 회수 보상 | 증가 없음. 역오염을 새 청소 실적으로 만들지 않음 |
| 털어내기 | 1회당 최대 **20** 감소. 통으로 실제 옮겨진 양만 차감 |
| 정상 청소 복귀 | 적재가 **67 미만**으로 내려간 뒤 |
| 별도 감점 | 헤라가 포화됐다는 이유만으로 점수 감점을 추가하지 않음 |

**10%의 기준은 벽 전체가 아니라 이번 접촉의 요청 작업량이다.** 100을 지운 뒤 10을 돌려놓는 방식이 아니다. 포화 상태에서는 기존 오염을 지우지 않고 10만 더한다. 따라서 “실효 청소 90%”로 계산하면 안 된다.

장비별 가격·작업 속도·따개비 및 광폭/열선 적재 배율 기획은 `08` §2에 남긴다. 다만 현재 오염 제거 경로는 공통 상수 +1.0을 직접 사용한다. **광폭·열선의 기존 적재 배율까지 코드에 반영됐다고 간주하지 않는다.** 품목별 차이 검증은 이 공통 동작 확인 뒤에 진행한다.

## 2. 표시와 조작

기존의 날 메시 3단계 표현을 유지한다. 수치의 정수 표시는 `1~33 / 34~66 / 67~100`이며, 실제 판정은 소수 적재량을 사용한다. 특히 66.99는 정상, 67.00은 포화다.

| 상태 | 플레이어가 보는 것 |
|---|---|
| 낮은 적재 | 헤라 끝에 얇게 붙은 오염 |
| 포화 직전 | 두꺼워지고 처지는 오염. 곧 비워야 한다는 예고 |
| 포화 | 날 전체의 오염, 핫바 적색 표시. `헤라가 찼습니다. 통에 털어 주세요.`를 진입 시 한 번 표시 |
| 비우기 | 한 번 털 때마다 날의 오염과 게이지가 함께 줄어듦 |

적재 100에서 두 번 털면 **60**, 적재 67에서 한 번 털면 **47**이다. “포화를 풀려면 항상 두 번”이라고 안내하지 않는다. 통이 가득 차 실제로 받지 못하면 헤라 적재만 사라져서는 안 된다.

## 3. 청소한 오염물이 보상으로 이어지는 과정

**긁기 → 통에 털기 → 현장 대기장에서 응고 → 노란 분류 칸에 투입 → 점수·환급** 순서다. 응고 디스펜서를 “나중에 만들 기능”으로 빼면 청소 보상을 검증할 수 없다.

- 적재 100분은 액체 1.0유닛, 통 상한은 5.0유닛이다.
- 응고제는 현장 대기장에 무료·무한으로 비치한다. 상점 구매나 핫바 칸을 요구하지 않는다.
- 1회 분사로 통 안 액체를 응고한다. 기본 기획 단가는 1.0유닛당 덩어리 1개, 노란 칸 정분류 +32점·16₡다.
- 통째 투입해도 **통은 남는다**. 내용물만 각각 분류한다. 구판의 통 소멸 규칙은 폐기됐다.
- 1.0 미만 잔량의 덩어리·보상 환산은 별도 결정이 필요하다. 임의로 올림해 보상을 늘리거나 버림해 수거분을 없애지 않는다.
- 현재 코드는 액체량과 보상 가능한 양을 따로 보관한다. 재오염·쏟기·재수거로 같은 오염물의 보상이 늘지 않도록 이 구분을 응고·정산까지 이어야 한다.

액체 축적·쏟기·저장 코드는 존재한다. 응고 디스펜서와 최종 보상 연결은 별도 확인·구현 대상이며, 전체 경로를 완료로 표시하지 않는다.

## 4. 구현을 확인할 곳

대조 기준은 `origin/dev`의 `8f579de5`다.

| 위치 | 확인 내용 |
|---|---|
| `MD_ScrapeToolComponent.h` | `CanonicalScrapeLoadPerRemovedPercent = 1.0`, `SaturatedReverseContaminationRatio = 0.1` |
| `MD_ScrapeToolComponentPath.cpp` | 실제 제거 결과를 공통 +1.0 상수로 환산하는 경로 |
| `MD_ScrapeToolComponent.cpp` | 생성자의 옛 `ScrapeLoadPerRemovedPercent = 0.6`은 실제 오염 계산 기준이 아님. 혼동을 줄이도록 후속 코드 정리 필요 |
| `MD_ScrapeEvaluator.cpp` | 포화 시 제거를 하지 않고 접촉량만 계산하는 분기 |
| `MD_TrashBin`·저장 구조 | 액체량·보상량·수거 출처의 보존 |

9월 6일 [21b754af](https://github.com/RevStudio/ProjectATM/commit/21b754af30cfbf5768bdaf337e6ced2d93a43ee5)는 포화 상태에서 반복해서 긁으면 결국 지워지던 동작을 없앴다. 이번 합의는 그 방향을 유지한다. 커밋에 적힌 과거 테스트는 이 문서 작성 중 새로 실행한 결과가 아니다.

## 5. 플레이 확인 항목

- [ ] 같은 면에서 실제 제거율 10%가 늘면 기본 적재가 10 늘어나는가.
- [ ] 적재 66.99 / 67 / 67.01 / 100에서 정상과 포화가 정확히 나뉘는가.
- [ ] 포화된 채 같은 곳을 계속 긁어도 기존 오염이 줄지 않는가.
- [ ] 포화 중 적재량과 신규 회수 보상이 증가하지 않는가.
- [ ] 67에서 한 번 털면 47이 되고, 다시 정상적으로 닦이는가.
- [ ] 통 용량이 부족할 때 옮긴 양과 남은 적재가 일치하는가.
- [ ] 호스트·참가자에게 적재와 표면 변화가 같게 보이는가.
- [ ] 응고·분류·저장 복원 후에도 같은 수거분의 보상이 중복되지 않는가.

## 6. 폐기한 설명

| 이전 설명 | 현재 기준 |
|---|---|
| 오염 1%당 적재 +0.6 | **+1.0** |
| 67~99에서 제거 ×0.5 + 역오염 40% | **67부터 제거 없음 + 요청 작업량의 10% 역오염** |
| 모든 적재 단계에서 제거 ×1.0, 40%만 되돌림 | 폐기. 포화 중 일부 청소가 되는 안을 쓰지 않음 |
| 100에서만 청소 중단 | **67부터 중단** |
| 통째 투입하면 통 소멸 | 통 유지, 내용물 개별 판정 |
| 응고·분류는 이번 범위 아님 | 청소 보상 검증에 필요한 작업으로 포함 |
