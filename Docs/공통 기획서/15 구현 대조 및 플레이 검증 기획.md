## 1. 수도관은 폼건으로 쏴서 수리한다

**기획:** `02` §2.4, `08` §4.2. F는 수도관 수리 입력이 아니다. 한 발을 쏠 때 충전 25를 소비하고, 파열구에 맞으면 밀봉한다. 빗나가도 발사 비용은 든다.

**코드:** `MD_WaterPipe.cpp` 생성자는 수리 도구 태그만 설정한다. 부모 `MD_WallUtility`는 `bRepairRequiresToolInput`이 꺼져 있으면 `CanInteract → Interact → TryRepairWithEquippedTool`로 수리한다. 발사·충전 차감을 거치지 않는 경로가 남는다. Blueprint 기본값의 재정의 여부는 별도 확인 대상이다.

**작업:** 수도관의 도구 입력 제한, 상호작용 안내, 서버 수리 허용 경로를 함께 맞춘다. 발사체 수리는 유지한다. M03a·M03b 수리 대상도 같은 규칙을 쓴다.

**완료 조건:** 충전 0·24·25·100 각각에서 확인한다. F는 수리하지 않고, 25 미만은 발사할 수 없으며, 한 발은 정확히 25를 쓴다. 명중·밀봉 후 분출·위험 피해·추가 누수 감점이 멈춘다. 호스트와 참가자에게 동일하게 적용된다.

## 2. 감점은 대기장의 미분류 물건에만 붙인다

**기획:** `05` S−03은 **대기장 미분류 −6/개**, S−04 현장 미수거 감점은 삭제됐다. 현장에 남긴 벽 조각은 감점 없이 다음날로 넘어간다.

**코드:** `MD_GameModeBase`가 월드의 `AMD_WallPiece`를 세어 `Score.Penalty.UncollectedRemain`을 발행한다. `MD_ScoreTableData`에는 두 태그 모두 −6이 남아 있다. `UnsortedRemain`은 정의·표시 분류는 있지만 C++에서 정산 이벤트를 발행하는 지점을 찾지 못했다.

**작업:** 전역 벽 조각 감점을 제거하고, **현장 대기장의 범위**를 명시해 그 안의 미분류 물건을 집계한다. 빈 통 자체는 제외하고 내용물을 센다. 한 물건이 통 내용물과 구역 액터 양쪽에서 중복 집계되면 안 된다. 샘플 미납품은 퀘스트 실패 규칙을 쓴다.

**완료 조건:** 현장 벽 조각 3개는 이 항목의 감점 0. 대기장 미분류 고체 3개는 −18. 같은 고체 3개를 담은 통 1개도 −18, 빈 통은 0이다. 정분류된 물건과 한 번 처리한 당일 정산은 다시 세지 않는다.

**남은 세부 결정:** 대기장의 미응고 액체를 ‘개수’로 환산할지, 남은 동일 물건을 다음날에도 감점할지는 기존 문서에 명시가 없다. 구현자가 임의로 정하지 않도록 별도 항목으로 둔다. −6을 액체 0.2유닛마다 자동 적용하지 않는다.

## 3. 착수금

**기획:** `07` §2.2와 `12`. 비상 4일차는 무조건 0₡다. 정규일에만 호감도와 경고 배율을 적용한다.

| 중립 호감도 예 | 지급 |
|---|---:|
| 경고 없는 정규일 | 500₡ |
| 경고 다음 정규일 | 350₡ |
| 비상 4일차 | 0₡ |

**코드:** `MD_GameModeBase`는 경고 때 `NextDepositMultiplier=0.7`, 비상 때 0을 저장한다. 그러나 `MD_MerchantSubsystem::BeginDay`는 이를 읽지 않고 `bEmergencyDay ? 0.7 : 1`을 호감도 배율에 곱한다. 따라서 **비상 350₡는 중립 호감도일 때의 예**다. 호감도가 다르면 금액도 달라진다.

**작업:** 비상 0원 분기를 먼저 적용한다. 경고 배율은 다음 정규일의 실제 지급 계산에 반영한다. 지급 내역과 표시 금액을 일치시킨다.

**완료 조건:** 정상·경고·비상을 중립/높은/낮은 호감도로 각각 확인한다. 비상은 모두 0이다. 일자 전환·재접속·저장 불러오기로 같은 날 착수금을 두 번 받지 않는다.

## 4. 헤라 — 현재 구현을 기획 기준으로 채택

**2026-09-18 사용자 결정:** 적재 **+1.0**, **67부터 제거 중단**, 역오염 **10%**를 유지한다. +0.6·40%로 되돌리는 버그 수정 항목에서 제외하고, 문서와 옛 설정값을 정리하는 항목으로 바꾼다.

9월 6일 [21b754af](https://github.com/RevStudio/ProjectATM/commit/21b754af30cfbf5768bdaf337e6ced2d93a43ee5)는 포화돼도 반복해서 긁으면 지워지던 현상을 없애려는 변경이다. 최신 dev의 `MD_ScrapeToolComponent.h` 상수는 +1.0과 0.1이며 `MD_ScrapeToolComponentPath.cpp`의 실제 적재 계산은 +1.0을 사용한다. 생성자에 남은 +0.6 설정만 읽고 현재값을 판단하면 안 된다.

**포화 동작:** 기존 오염을 제거하지 않는다. 요청 작업량의 10%를 덧묻히고, 적재량과 신규 회수 보상은 증가시키지 않는다. 통에 털어 67 미만이 되면 정상 제거한다. 10%는 벽 전체 비율도, 지운 양의 일부를 복원하는 비율도 아니다.

**완료 조건:** 66.99/67/67.01/100 경계, 반복 긁기, 털기 후 정상 복귀, 보상 중복을 확인한다. 장비별 적재 배율 적용 여부는 별도 확인한다. 상세는 [헤라 오염 적재 구현](헤라%20오염%20적재%20구현.md)을 따른다.

## 5. 게임오버한 계약은 저장에서 다시 열 수 없다

**기획:** `02` §10.5, `12` §5. 실패한 계약을 복원하는 자동·수동 저장을 무효화한다. 개인 로어 기록·설정·다른 계약 저장은 보존한다.

**코드:** `HandleGameOver`는 `ClearSnapshot`, 오염 컨텍스트 초기화, 계약 초기화를 수행한다. `ClearSnapshot`은 메모리 구조체를 비운다. `MD_SaveSlotManager`·`MD_SaveSlotStore`의 파일과 목록을 해당 계약의 게임오버에 연계해 제거하는 호출은 확인되지 않았다. PR #155에서 불러오기 화면까지 연결돼 있어 실제 파일 처리도 필요하다.

**작업:** 실패 계약에 속한 슬롯을 식별해 파일·인덱스·선택된 불러오기 상태를 함께 정리한다. 여러 자동 슬롯과 수동 슬롯도 같은 계약이면 대상이다. 식별 기준 없이 모든 세이브를 지우지 않는다. 저장 중 게임오버가 나면 늦게 완료된 저장이 슬롯을 되살리지 않도록 한다.

**완료 조건:** 게임오버 직후, 로비 복귀 후, 앱 재실행 후 모두 실패 계약을 재개할 수 없다. 로어 수집과 다른 계약 저장은 남는다. 목록에서 숨기기만 하지 말고 실제 삭제 또는 로드 거부까지 확인한다.

## 6. 카트리지는 한 개당 +25다

**기획:** `08` §4.2. 폼 카트리지 55₡는 **+25**다. 0→100은 4개·220₡. 열선 배터리는 기존 +90초·35₡를 유지한다.

**코드:** `MD_ToolChargeItemDefinition::CanGrant/Grant`가 품목별 보충량 대신 대상 도구의 `MaxCharge`를 전달한다. 1회 구매가 만충으로 이어진다. PR #138의 지급 구조 개편을 유지하되 충전물별 양을 정의해야 한다.

**완료 조건:** 폼 잔량 0/50/90에서 1개 구매 후 각각 25/75/100. 만충이면 구매 불가이며 크레딧도 차감하지 않는다. 구매 수량만큼 금액과 보충량을 적용하되 초과 구매로 돈만 사라지지 않게 한다. 기본 4개 구매는 220₡·100충전이다. 열선 배터리까지 +25로 바뀌지 않아야 한다.

## 7. 핫바는 6칸이다

**기획:** `08` §7. 헤라·절단기·스캐너·지지대·테이프·산소 캔처럼 6종을 함께 들 수 있다. 여기에 폼건까지 더하면 7종이므로 교체하거나 팀원과 나눈다.

**코드:** `MD_EquipHotbarComponent`의 생성·초기화에 `ToolEntries.SetNum(4)`가 남아 있고, `MD_ToolDefinition` 지급 조건도 `GetSlotCount()!=4`를 검사한다. 배열 크기 한 곳만 바꿔서는 상점 지급 조건이 어긋난다.

**작업:** 보관 칸 수, 숫자키 1~6, 스크롤, HUD·인벤토리, 드래그 이동, 구매·판매, 저장·복원을 맞춘다. 예전 4칸 저장은 앞의 네 칸을 보존하고 남은 두 칸을 빈 칸으로 복원하는 것을 기준으로 한다.

**완료 조건:** 5·6번 칸에서 구매·사용·판매·이동이 되고 재접속·불러오기 후에도 물건과 잔량이 남는다. 기존 4칸 저장의 아이템도 유실되지 않는다.

**진행 확인:** 카드 없는 상태의 보고는 막히고, 수리→카드 획득→브릭스 보고→M03b로 이어져야 한다. 로어는 조사·팀 공유·개인 저장·코덱스 열람까지 확인한다. 마감 마커는 조건 검사와 반복 의뢰 진행 연결까지 확인한다.

클래스가 있거나 테스트 레벨에서 동작했다는 이유로 `L_Ocean` 배치 완료로 표시하지 않는다. 검사 시 맵 리비전·액터 이름/경로·연결 대상·통과 결과를 남긴다. 현재 인스턴스 목록은 **미확인**이다.

## 9. 청소·마감 의뢰를 실제 행동에 연결한다

**정정:** “퀘스트는 납품만 진행된다”는 설명은 최신 메인 퀘스트에는 맞지 않는다. PR #140에서 **메인 Interaction 진행·카드 확보·브릭스 단계 전환**이 추가됐다. 남은 문제는 반복 의뢰의 청소·마감·복합 진행이다.

`EMD_QuestObjectiveType`에는 `Cleanup/Sealing/Composite`가 있지만 상인 서브시스템에서 반복 진행을 올리는 해당 경로는 찾지 못했다. `MD_SectorCloseoutMarker::TryCloseout`은 제출 시 닫힘과 기본 점수만 처리하며 주석에서도 잔해 등 조건 검사를 후속 작업으로 둔다. 마커 배치만으로 기획이 충족되지는 않는다.

**에셋 확인:** 8개 반복 DA가 모두 회수 타입이라는 것은 제보다. 개별 `.uasset` 속성은 이번에 읽지 않았다. 아래의 기존 목표를 기준으로 대조하며 실제 속성값을 추정하지 않는다.

| 의뢰 | 필요한 목표 | 진행을 인정하는 행동 |
|---|---|---|
| R02 | 손상 허용 회수 | 해당 샘플 2개 납품 |
| R05 | 마감 | B1-05 부속 격벽 철거 + 청소 조건 충족 + 마감 제출 |
| R06 | 조사 행동을 세는 청소 계약 | 서로 다른 해수 스캔 지점 3곳 완료. 운반·납품 없음 |
| R07 | 청소 | 지정 표류 폐기물 5개를 현장 대기장에서 정분류 |
| R08 | 손상 허용 회수 | 생물 샘플 2개 납품 |
| R09 | 복합 | 항로 부유물 2개 정리 + 진입구 청소·마감 + C급 샘플 1개 납품 |
| R10 | 온전한 회수 | B급 샘플 2개 Intact 납품 |
| R11 | 온전한 회수 | A급 코어 1개 Intact 납품 |

**완료 조건:** R05는 샘플 없이 끝나고, R06은 같은 지점을 반복 스캔해도 늘지 않으며, R07은 손에 들었다 놓기만 해서는 진행되지 않는다. R09는 샘플만 내도 완료되지 않는다. 서버가 한 번만 반영하고 날짜·저장 복원 후에도 유지한다. 비상 4일차가 열리면 수락한 반복 의뢰를 유지한다.

**점수 중복 금지:** R05 +40은 기본 구역 마감 점수 포함, R09 +110은 마감 +40과 C급 회수 +70의 합이다. 이미 받은 마감 점수 위에 의뢰 총액 전체를 추가하지 않는다. 나머지 보수·호감도는 전용 `05`의 기존 표를 유지한다.

## 10. 응고해서 분류할 때까지 청소 보상을 연결한다

**기획:** `02` §1.2.6. 통에 모은 액체를 현장 대기장에서 무료 응고제로 굳히고 노란 분류 칸에 넣는다. 1.0유닛당 기본 +32점·16₡다. 응고 동작 자체에는 보상을 주지 않는다.

**코드:** 액체량·보상량·수거 출처·쏟기·저장 코드는 있다. 응고 디스펜서와 액체를 분류 가능한 덩어리로 바꾸는 연결은 소스에서 찾지 못했다. Blueprint 전용 기능의 존재까지 부정하는 결과는 아니므로 실제 맵/에셋의 누락은 별도 확인한다.

**작업:** 대기장 디스펜서, 대상 통 선택, 액체→고체 변환, 분류 판정, 점수·환급 표시를 한 경로로 완성한다. 무료·무한이며 핫바 칸을 쓰지 않는다. 통은 응고·투입 뒤에도 남는다.

**완료 조건:** 새로 수거한 정상 보상량 1.0유닛을 응고해 정분류하면 +32점·16₡를 정확히 한 번 받는다. 빈 통·중복 입력은 변화가 없다. 잘못된 칸은 기존 오분류 규칙을 따른다. 응고 전 액체를 통째로 붓는 경우에는 기존 기획대로 보상 0이며 액체가 소멸한다. 변환 실패나 동시 사용으로 액체·덩어리가 중복 생성되거나 유실되지 않는다.

**남은 세부 결정:** 액체 0.2 또는 1.4유닛의 고체 표현·정산 방식은 기존 문서에 없다. 현재 코드의 액체량과 보상 가능한 양 구분도 유지해야 한다. 재오염 반복 수거로 새 보상을 만들지 않으며, 기록된 보상 가능한 양을 응고 결과까지 보존한다. 잔량 처리안을 정하기 전에는 임의 올림·버림으로 구현을 완료하지 않는다.

## 11. 작업 순서와 플레이 검증

먼저 **무료 수리·잘못된 감점·착수금·게임오버 복원·충전량**을 바로잡는다. 보상과 비용이 틀린 상태에서는 플레이 결과로 난이도를 판단하기 어렵다. 핫바 6칸도 맞춰 의도한 장비 편성이 가능하게 한다.

그다음 **맵 배치 확인 → 구역 마감 조건·의뢰 진행 → 응고·분류 보상**을 연결한다. 헤라는 합의한 현행 동작을 유지하고 옛 +0.6 설정처럼 혼동을 만드는 부분을 정리한다.

최소 플레이 확인은 아래 네 가지다. 전 항목은 **아직 미실행**이며 실제 확인한 뒤 완료로 표시한다.

1. **수리와 구매:** F 우회 차단, 한 발 −25, 카트리지 +25, 6칸 장비 사용.
2. **하루 종료:** 현장 잔해 감점 0, 대기장 미분류 −6, 경고/비상 착수금, 실패 저장 재개 차단.
3. **퀘스트:** M03a→M03b, 활성 로어 6종, 마감 4곳, R05·R06·R07·R09의 서로 다른 완료 행동.
4. **청소 보상:** 정상 긁기→67 포화→털기→응고→분류→보상. 재오염·쏟기·복원으로 보상이 늘지 않는지도 확인한다.

각 확인은 호스트와 참가자가 있는 세션에서 결과·진행도·잔량이 같은지도 본다. 이 경로가 성립한 뒤 청소/수리/운반의 순서를 고르는 재미와 10분 동안의 반복 피로를 비교한다. 기능이 끊겨 못 끝내는 상황과 완성된 작업이 재미없는 상황을 같은 문제로 판단하지 않는다.
